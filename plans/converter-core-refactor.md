# Plan: Рефакторинг ядра конвертера (Converter + worker)

> Source SPEC: `spec/converter-core-refactor.md`

## Architectural decisions

Решения, которые действуют во всех фазах:

- **Модуль**: всё, что относится к конвертации (Converter, пайплайн, воркер, реестры, типы, декодеры, энкодеры, агрегаторы, подготовка SVG), живёт в одном модуле `conversion`. `WorkerPool`, хелпер ресайза канваса и хелпер белой подложки остаются в общих утилитах.
- **Задача конвертации** (`ConvertTask`): MIME-тип, blob URL источника, `OutputTarget`, весь объект входных настроек (`inputSettings`, сейчас `{ pdf }`) и необязательный результат подготовки (`ImageBitmap`).
- **Кадр** (`Frame`): `OffscreenCanvas | Blob`. Готовый `Blob` проходит пайплайн без изменений.
- **Декодер**: `(task) => AsyncGenerator<Frame>`. Только декодирует и ничего не знает о resize и encode.
- **Реестр входных форматов**: `Record<MIMEType, InputFormatEntry>`. Запись содержит ленивый `load` декодера, необязательный `prepare` (выполняется в main thread и возвращает bitmap) и необязательный флаг `selfResizing`.
- **Реестр выходных форматов**: mapped type `{ [F in OutputFormat]: OutputFormatEntry<F> }`. Запись содержит ленивый энкодер `(canvas, settings: OutputSettingsMap[F])`, необязательный ленивый агрегатор и флаг `alpha`. Альфа-канал есть у PNG, TIFF и WebP; у JPEG, BMP, GIF и PDF его нет.
- **Пайплайн**: `ConvertTask → Promise<Blob[]>`. Шаги: decode → resize (если включён и формат не `selfResizing`) → белая подложка (если у выхода нет `alpha`) → encode. Один и тот же код работает в воркере и в main thread.
- **Протокол воркера**: `{ ok: true, blobs: Blob[] } | { ok: false, message: string }`. Сбой инфраструктуры воркера (`onerror` или reject пула) — это единственный повод для fallback'а в main thread.
- **Результат обработки файла**: всегда `Blob[]`.
- **Все импорты в реестрах ленивые**, чтобы воркер не тянул модули, которым нужен DOM.
- **Toolchain**: pnpm запускается через `cmd.exe`, git — через `git.exe`. После каждой фазы выполняются typecheck и lint, и каждая фаза — отдельный коммит.

## Phase 1: Модуль conversion и generic WorkerPool

**User stories**: 19, 20, 35

### What to build

Всё, что относится к конвертации, переезжает в модуль `conversion` без изменения логики. `WorkerPool` становится действительно generic: фабрика воркеров передаётся в конструктор, а Converter передаёт фабрику воркера конвертации. Стор импортирует Converter из нового места.

### Acceptance criteria

- [ ] Файлы конвертации лежат в модуле `conversion`, в старых местах ничего не осталось.
- [ ] `WorkerPool` не импортирует конкретный воркер и принимает фабрику в конструкторе.
- [ ] typecheck и lint проходят, сборка проходит.
- [ ] Конвертация в браузере работает как раньше (проверка на паре форматов).

## Phase 2: Реестр выходных форматов

**User stories**: 3, 4, 5, 6, 7, 22, 24

### What to build

Реестр выходных форматов с обязательной записью для каждого `OutputFormat` заменяет `switch` в encode и `switch` в merge. JPEG, PNG и WebP создаются одной фабрикой canvas-энкодеров, которая учитывает `quality`, если он есть в настройках. У PDF и GIF в записи есть ленивые агрегаторы. Converter вычисляет признак «сливать в один файл» так: у формата есть агрегатор и в настройках включено `merge`. Merge идёт по одному пути через реестр. Флаг `alpha` добавляется в записи уже сейчас, но пока не используется.

### Acceptance criteria

- [ ] Если удалить запись для любого выходного формата, TypeScript выдаёт ошибку.
- [ ] Энкодер и агрегатор получают `OutputSettingsMap[F]` без приведений типов.
- [ ] В encode и merge не осталось `switch` по выходному формату.
- [ ] GIF-агрегатор не попадает в бандл воркера (все импорты ленивые).
- [ ] Merge в PDF и в анимированный GIF работает как раньше.

## Phase 3: Трассирующая пуля пайплайна (JPEG/PNG/WebP, BMP, HEIC)

**User stories**: 1, 2, 8, 9, 17, 23 (частично), 24

### What to build

Вводятся контракты `ConvertTask`, `Frame` и декодера, реестр входных форматов и общий пайплайн (decode → resize → encode). Декодеры JPEG/PNG/WebP (один загрузчик на три MIME), BMP и HEIC переписываются в async-генераторы кадров. Из них убираются resize и encode, при этом сохраняется HEIC-fallback через `createImageBitmap`. Воркер для этих форматов вызывает пайплайн и отвечает структурированным сообщением. Converter разворачивает этот ответ. Fallback этих форматов в main thread вызывает тот же пайплайн. TIFF, GIF, PDF и SVG временно идут по старому пути через гибридный диспатч в воркере.

### Acceptance criteria

- [ ] Декодеры JPEG/PNG/WebP, BMP и HEIC только отдают кадры и не импортируют encode или resize.
- [ ] Воркер больше не выбрасывает ошибки через `setTimeout`. Ошибка файла приходит как `{ ok: false, message }` с читаемым сообщением.
- [ ] Для перенесённых форматов воркер и fallback вызывают один и тот же пайплайн.
- [ ] Конвертация JPEG/PNG/WebP/BMP/HEIC во все 7 выходных форматов работает, включая ресайз.
- [ ] Старые форматы (TIFF/GIF/PDF/SVG) по-прежнему работают.

## Phase 4: Многокадровые декодеры (TIFF, GIF, PDF)

**User stories**: 12, 14, 21, 29

### What to build

Декодеры TIFF, GIF и PDF становятся async-генераторами, которые отдают кадры по одному. Декодер PDF берёт `resolution` и `rotation` из `task.inputSettings.pdf`. Для PDF→PDF без ресайза он отдаёт готовые блобы страниц, полученные через pdf-lib, с учётом поворота. В остальных случаях он отдаёт отрендеренные канвасы. Задача несёт весь объект входных настроек. Пока Converter собирает его из имеющихся PDF-настроек. Разделение декодеров на single-page и multi-page исчезает.

### Acceptance criteria

- [ ] Декодеры TIFF, GIF и PDF не импортируют encode или resize.
- [ ] PDF→PDF без ресайза остаётся векторным и учитывает поворот. PDF→PDF с ресайзом растеризуется.
- [ ] Отдельного поля PDF-настроек в задаче нет, есть только `inputSettings`.
- [ ] Многостраничные PDF/TIFF/GIF конвертируются во все выходные форматы, merge работает.
- [ ] В структуре декодеров нет папок single-page и multi-page.

## Phase 5: SVG через шаг подготовки

**User stories**: 10, 11, 18, 30, 31

### What to build

У записи SVG в реестре входных форматов появляется `prepare`: это существующая растеризация SVG в целевой размер в main thread. Формат помечается как `selfResizing`. Converter выполняет `prepare`, если он есть в записи, кладёт bitmap в задачу и в transferables, а перед fallback'ом выполняет `prepare` заново. Декодер SVG только рисует bitmap на канвас: логика белого фона и smoothing из него удаляется. Временно, до фазы 7, белая подложка для SVG сохраняется в пайплайне, чтобы не было регрессии. После этой фазы гибридный диспатч в воркере исчезает, и воркер становится тонкой обёрткой над пайплайном.

### Acceptance criteria

- [ ] В Converter нет частных `if` для SVG, подготовка берётся из реестра.
- [ ] Процентный ресайз SVG применяется ровно один раз, размер результата правильный.
- [ ] При увеличении SVG растеризуется сразу в целевой размер и не теряет качество.
- [ ] Fallback для SVG не падает на detached bitmap.
- [ ] Воркер не содержит логики выбора декодера.
- [ ] SVG → JPEG/BMP/GIF/PDF по-прежнему получает белый фон.

## Phase 6: Тонкий Converter

**User stories**: 13, 15, 16, 23, 27, 28, 33, 34

### What to build

Converter становится оркестратором. Одна функция запуска задачи: подготовка, затем воркер; при сбое воркера — повторная подготовка и пайплайн в main thread. Ответ `{ ok: false }` пробрасывается как ошибка файла без fallback'а. Результаты всех файлов обрабатываются по одному пути диспатча: если результат один, используется исходное имя, если их больше, добавляются суффиксы `_1`, `_2`, …; `sourceId` проставляется. Стор передаёт в Converter весь объект входных настроек. Ошибка одного файла не блокирует остальные.

### Acceptance criteria

- [ ] В Converter нет методов `convertX` и нет `switch` по MIME-типу.
- [ ] Битый файл даёт ошибку без повторной обработки в main thread, остальные файлы конвертируются.
- [ ] При принудительно сломанном воркере все форматы отрабатывают в main thread.
- [ ] У одностраничного TIFF/PDF/GIF результат без суффикса `_1`, у многостраничного суффиксы `_1…_N`.
- [ ] Конструктор Converter принимает весь объект входных настроек.
- [ ] Merge PDF/GIF работает, имя результата `Merged-<timestamp>`.

## Phase 7: Белая подложка для всех входов

**User stories**: 25, 26, 36

### What to build

Рядом с хелпером ресайза в общих утилитах появляется хелпер белой подложки. Пайплайн применяет его к каждому канвасу любого входа, если у выходного формата нет альфа-канала: для этого используется флаг `alpha` из реестра выхода. Временный частный случай для SVG из фазы 5 удаляется. Всё это — отдельный коммит, чтобы его можно было откатить независимо.

### Acceptance criteria

- [ ] Прозрачные PNG/WebP/GIF/HEIC/SVG при конвертации в JPEG, BMP, GIF и PDF получают белый фон.
- [ ] При конвертации в PNG, TIFF и WebP прозрачность сохраняется.
- [ ] Решение о подложке принимается только по флагу `alpha` из реестра.
- [ ] Полный smoke-прогон по матрице из спеки: 9 входов × 7 выходов, merge PDF/GIF, принудительный fallback, битый файл.
