# SPEC: Рефакторинг ядра конвертера (Converter + worker)

## Problem Statement

Ядро конвертации (класс Converter, воркер, декодеры, энкодеры, агрегаторы) содержит много повторяющегося кода, и его трудно расширять:

- В Converter семь почти одинаковых методов `convertX`. Каждый повторяет схему «попытка в воркере → лог ошибки → dynamic import того же декодера в main thread». Отличаются они только модулем и парой полей задачи.
- Ветки обработки single-page и multi-page файлов почти идентичны. Разница только в том, как формируется имя.
- Слияние (merge) для PDF и GIF — это `switch` с одинаковым кодом диспатча.
- Воркер повторяет тот же `switch` по MIME-типам, что и fallback в Converter.
- Каждый декодер сам делает resize и encode, и этот хвост одинаковый во всех.
- Логика выходных форматов разнесена по двум `switch`: encode и merge.
- Входные настройки (сейчас только PDF) проброшены отдельными аргументами через конструктор, задачу и воркер. Каждая новая настройка требует менять все эти места.
- При любой ошибке файл повторно обрабатывается в main thread, даже если он просто битый. Ошибки из воркера приходят как `ErrorEvent` без стека.
- Белая подложка для форматов без прозрачности применяется только к SVG. Прозрачные PNG/WebP/GIF/HEIC при конвертации в JPEG и подобные форматы получают чёрный фон.

Из-за этого добавление нового входного или выходного формата требует правок в 4–6 местах. Легко что-то забыть, и компилятор об этом не предупредит.

## Solution

Ядро перестраивается вокруг двух декларативных реестров и одного общего пайплайна:

- **Реестр входных форматов** сопоставляет MIME-тип с описанием: ленивый загрузчик декодера, необязательный шаг подготовки в main thread и флаг «декодер сам отдаёт кадры в целевом размере».
- **Реестр выходных форматов** сопоставляет выходной формат с описанием: ленивый энкодер, необязательный ленивый агрегатор (merge) и флаг поддержки прозрачности.
- **Декодеры** только декодируют: превращают исходный файл в асинхронную последовательность кадров (канвасов, в особых случаях готовых блобов). Про настройки вывода они не знают.
- **Общий пайплайн** принимает задачу и возвращает массив блобов. Он применяет resize, белую подложку и encode одинаково для всех входов. Один и тот же пайплайн работает и в воркере, и в fallback-режиме в main thread.
- **Converter** становится тонким оркестратором: одна функция запуска задачи с fallback'ом, один путь диспатча результатов, один путь merge.

Для пользователя приложения поведение не меняется, за исключением намеренных изменений:
- прозрачные изображения при конвертации в форматы без альфа-канала получают белый фон вместо чёрного;
- одностраничные результаты из многостраничных форматов больше не получают суффикс `_1`;
- битые файлы не обрабатываются повторно в main thread.

Для разработчика добавление формата сводится к одной записи в реестре и одному-двум файлам, а полноту реестров проверяет TypeScript.

## User Stories

1. Как разработчик, я хочу добавить новый входной формат одной записью в реестре и одним файлом декодера, чтобы не править Converter, воркер и fallback.
2. Как разработчик, я хочу, чтобы новый декодер описывал только «байты → кадры», чтобы не повторять в нём код resize и encode.
3. Как разработчик, я хочу добавить новый выходной формат одной записью в реестре и файлом энкодера, чтобы не трогать `switch` в разных местах.
4. Как разработчик, я хочу, чтобы TypeScript ругался, если для какого-то выходного формата нет записи в реестре, чтобы формат нельзя было забыть.
5. Как разработчик, я хочу, чтобы энкодер получал настройки строго своего формата, чтобы не писать проверки и приведения типов.
6. Как разработчик, я хочу включить поддержку merge для формата, добавив в его запись агрегатор, чтобы Converter подхватил это автоматически.
7. Как разработчик, я хочу, чтобы признак «нужно сливать в один файл» вычислялся из реестра и настроек, чтобы не поддерживать его вручную.
8. Как разработчик, я хочу, чтобы воркер и fallback в main thread выполняли один и тот же код пайплайна, чтобы их поведение не расходилось.
9. Как разработчик, я хочу, чтобы воркер был тонкой обёрткой над пайплайном, чтобы в нём не было логики выбора декодера.
10. Как разработчик, я хочу описать шаг подготовки формата в main thread (например, растеризацию SVG через DOM) прямо в записи реестра, чтобы в Converter не было частных `if` для отдельных форматов.
11. Как разработчик, я хочу явно пометить формат флагом «сам отдаёт кадры в целевом размере», чтобы пайплайн не ресайзил их повторно и было понятно почему.
12. Как разработчик, я хочу, чтобы декодер мог отдать готовый блоб вместо канваса (например, PDF→PDF без растеризации), чтобы поддерживать сквозные сценарии без отдельного механизма.
13. Как разработчик, я хочу передавать в задачу весь объект входных настроек, чтобы новая входная настройка формата не требовала менять Converter, задачу и воркер.
14. Как разработчик, я хочу, чтобы декодер сам брал из задачи нужные ему данные, чтобы Converter не знал о деталях конкретных форматов.
15. Как разработчик, я хочу иметь одну функцию «запустить задачу в воркере, при сбое воркера выполнить в main thread», чтобы не было семи копий этой логики.
16. Как разработчик, я хочу, чтобы fallback в main thread срабатывал только при сбое инфраструктуры воркера, а не при ошибке в самом файле, чтобы битые файлы не обрабатывались дважды.
17. Как разработчик, я хочу, чтобы воркер возвращал ошибки обработки как структурированный ответ с сообщением, чтобы получать читаемые ошибки вместо `ErrorEvent` без стека.

20. Как разработчик, я хочу, чтобы всё, что относится к конвертации, лежало в одном модуле, чтобы было понятно, где искать и куда добавлять код.
21. Как разработчик, я хочу, чтобы разделение декодеров на single-page и multi-page исчезло, чтобы структура отражала единый контракт.

27. Как пользователь, я хочу, чтобы результат конвертации одностраничного файла назывался так же, как исходник, даже если формат многостраничный (TIFF/PDF/GIF), чтобы не получать лишний суффикс `_1`.
28. Как пользователь, я хочу, чтобы страницы многостраничного файла получали суффиксы `_1`, `_2`, …, как и раньше.
29. Как пользователь, я хочу, чтобы PDF→PDF без ресайза по-прежнему делился на страницы без растеризации и с учётом поворота, чтобы сохранялось векторное качество.
30. Как пользователь, я хочу, чтобы SVG по-прежнему растеризовался сразу в целевой размер, чтобы при увеличении не терялось качество.

32. Как пользователь, я хочу, чтобы слияние в PDF и в анимированный GIF работало как раньше.

35. Как разработчик, я хочу, чтобы каждый шаг рефакторинга был отдельным коммитом, после которого приложение собирается и работает, чтобы изменения было легко ревьюить и откатывать.

## Implementation Decisions

### Модули

- **Модуль conversion** — новый общий модуль, куда переезжает всё, что относится к конвертации: Converter, пайплайн, воркер, оба реестра, типы, декодеры, энкодеры, агрегаторы, шаг подготовки SVG.
- **Converter** — оркестратор. Отвечает за запуск задач с fallback'ом, диспатч результатов в стор, merge. Не знает о конкретных форматах.
- **Пайплайн** — функция «задача → массив блобов». Загружает декодер по MIME из реестра входа, итерирует кадры, для каждого канваса применяет resize (если он нужен и формат не помечен как self-resizing), затем белую подложку (если у выходного формата нет альфа-канала), затем энкодер из реестра выхода. Готовые блобы пропускает без изменений.
- **Воркер** — тонкая обёртка: принимает задачу, вызывает пайплайн и отвечает структурированным сообщением.
- **Реестр входных форматов** — индексируется по MIME-типу (так хранит тип `SourceFile`). Запись содержит ленивый загрузчик декодера, необязательный шаг подготовки в main thread и необязательный флаг self-resizing. JPEG, PNG и WebP ссылаются на один загрузчик.
- **Реестр выходных форматов** — индексируется по выходному формату через mapped type, чтобы запись была обязательна для каждого формата, а энкодер и агрегатор получали настройки именно своего формата. Запись содержит ленивый энкодер, необязательный ленивый агрегатор и флаг поддержки альфа-канала.
- **Фабрика энкодеров для canvas** — одна фабрика создаёт энкодеры JPEG/PNG/WebP через `convertToBlob` и учитывает качество там, где оно есть в настройках.
- **WorkerPool** — остаётся в общих утилитах, но принимает фабрику воркеров в конструкторе.
- **Хелпер белой подложки** — добавляется к общим утилитам рядом с хелпером ресайза канваса.

### Контракты

- **Задача конвертации**: MIME-тип, blob URL источника, выходной target, весь объект входных настроек и необязательный результат подготовки (bitmap).
- **Кадр**: либо `OffscreenCanvas`, либо готовый `Blob`.
- **Декодер**: функция задачи, которая возвращает асинхронную последовательность кадров (async generator). Кадры отдаются по одному, поэтому в памяти не держатся все страницы сразу.
- **Ответ воркера**: либо «успех» с массивом блобов, либо «ошибка» с сообщением. Ошибки обработки файла передаются этим ответом, а не повторным выбрасыванием через `setTimeout`.
- **Результат обработки файла** — всегда массив блобов.

### Поведение

- **Fallback**: при ответе воркера «ошибка» ошибка пробрасывается как ошибка файла, без fallback'а. При сбое самого воркера (`onerror` или отказ в пуле) задача выполняется в main thread через тот же пайплайн. Шаг подготовки перед fallback'ом выполняется заново, потому что bitmap уже передан в воркер и стал detached.
- **Подготовка**: если у формата есть шаг подготовки, Converter выполняет его в main thread перед отправкой задачи и кладёт bitmap в список transferables.
- **SVG**: шаг подготовки — существующая растеризация SVG в целевой размер, формат помечен как self-resizing. Декодер SVG только рисует bitmap на канвас. Отдельная логика белого фона и smoothing из него удаляется: белый фон делает пайплайн, а smoothing при отрисовке в тот же размер ничего не меняет.
- **PDF→PDF без ресайза**: декодер PDF отдаёт готовые блобы страниц, полученные через pdf-lib, с учётом поворота, как сейчас. В остальных случаях отдаёт отрендеренные канвасы.
- **Белая подложка**: пайплайн применяет её для всех входов, если у выходного формата нет альфа-канала. Флаги: PNG, TIFF, WebP поддерживают альфа-канал; JPEG, BMP, GIF, PDF — нет. Это повторяет текущее правило для SVG.
- **Merge**: включён, если у выходного формата есть агрегатор и в настройках включено слияние. Агрегатор загружается лениво и вызывается только в main thread. Имя результата остаётся `Merged-<timestamp>`.
- **Именование**: если результатов больше одного, к каждому добавляется суффикс с номером от 1; если результат один, используется исходное имя. `sourceId` проставляется, как сейчас.
- **Общий fetch источника** не выносится в хелпер: разным декодерам нужны разные представления (`blob`, `arrayBuffer`, `text`).

### Порядок реализации (отдельные коммиты, после каждого приложение собирается и работает)

1. Перенос файлов в модуль conversion без изменения логики; `WorkerPool` начинает принимать фабрику воркеров.
2. Реестр выходных форматов и фабрика canvas-энкодеров вместо `switch` в encode; merge в Converter через реестр.
3. Новый контракт декодеров (async-генераторы кадров), реестр входных форматов с подготовкой и флагом self-resizing, общий пайплайн, структурированный протокол ответа воркера.
4. Converter: единая функция запуска задачи с fallback'ом только при сбое воркера, единый путь обработки результатов, новое правило именования, весь объект входных настроек вместо настроек только PDF.
5. Белая подложка в пайплайне для всех входов.

## Out of Scope

- Автотесты, в том числе vitest browser mode с фикстурами. Это отдельная задача на будущее.
- Сквозные конвертеры для других пар форматов (например, GIF→GIF с сохранением палитры, JPEG→JPEG без перекодирования) и отдельный реестр прямых конвертеров.
- Потоковая передача кадров из воркера в main thread по одному: протокол остаётся «запрос → массив блобов».
- Изменения UI, стора (кроме передачи в Converter всего объекта входных настроек) и набора поддерживаемых форматов.
- Изменения алгоритмов декодирования и кодирования (BMP-парсер, HEIC, TIFF, GIF, pdf.js-рендер), кроме адаптации к новому контракту.
- Новые входные настройки для форматов, кроме PDF.

## Further Notes

- **Проверка**: typecheck и lint после каждого шага. После шагов 3–5 — ручной smoke-прогон в браузере по матрице:
  - все 9 входных форматов, включая прозрачный PNG и многостраничные PDF/TIFF/GIF, в каждый из 7 выходных;
  - merge для PDF и GIF;
  - принудительный fallback (временно ломаем воркер и убеждаемся, что main thread отрабатывает);
  - битый файл: ошибка без повторной обработки в main thread, остальные файлы конвертируются.
- Намеренные изменения поведения:
  - белый фон вместо чёрного для прозрачных входов в форматах без альфа-канала;
  - отсутствие суффикса `_1` у одностраничных результатов многостраничных форматов;
  - отсутствие fallback'а при ошибке в самом файле.
- Toolchain: в WSL pnpm запускается через `cmd.exe`, git — через `git.exe`.
